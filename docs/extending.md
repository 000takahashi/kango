# 会社と規則の足し方

勘合を育てる人のための手順です。会社一覧の列の意味と審査の方針は [CONTRIBUTING.md](../CONTRIBUTING.md) にあります。

## 会社を足す・直す

### 1. 公式の住所を、その会社自身のページで確かめる

いちばん大事な手順です。会社一覧は「青」を決める部分なので、ここに偽の住所が混ざると偽サイトが青になります。

- **その会社自身のページ**（フィッシングへの注意のお知らせ、よくある質問、送信元のメールアドレスの案内など）で、公式の住所が書かれているところを探します。ニュース記事・まとめサイト・検索結果の広告は根拠にしません。
- **グループ会社の住所も確かめます。** 本物の連絡が別の住所から来ることがあります（例：三井住友カードの `vpass.ne.jp`、ドコモの `nttdocomo.co.jp`）。抜けると、本物の連絡が「似せた住所」として赤になります。
- 確かめた日を `checked` に入れます。公式のページで確かめきれなかった会社は、`checked` を空にしておきます（README の「できないこと」にも数が出ます）。

### 2. `data/brands.csv` を直す

| 列 | 気をつけること |
|---|---|
| `id` | 英小文字の短い名前。台帳に入る値なので、一度決めたら変えない。 |
| `kind` | 契約している人だけに連絡が来る会社は `contract`、誰にでも来うる会社・機関（配送・郵便・役所）は `everyone`。 |
| `words` | 文面にあれば「この会社を名乗っている」とみなす言葉。**短すぎる言葉は使わない**（例：`au` は他の言葉の中にも出てくるので、`au pay`・`au id` のように長くする）。 |
| `domains` | 公式の住所。下の住所（`*.domain`）も公式とみなすので、**誰でも下の住所を作れるもの（共有のホスティングなど）は入れない**。 |
| `stems` | 偽の住所に紛れ込みやすい名前の断片。**短すぎると、関係のない住所まで「似せた住所」として赤にしてしまう**ので、会社をはっきり指す長さにする。 |

### 3. 同梱データを作り直して、テストを足す

```sh
python3 scripts/sync_brands.py          # Python と Swift の同梱データを作り直す
cd python && python -m pytest -q        # Python のテスト
```

- 本物の住所が青になる見本を、`python/tests/test_judge.py` の `test_official_subsidiary_domains_are_not_red` と、Swift の同じテストに1行ずつ足します。
- Pull Request には、確かめた**公式ページの URL**を必ず書きます。管理者が自分で開いて確かめてから取り込みます。

## 規則を足す・直す

### 規則を考える時の約束

- **青は、何か1つでも割符が合った時だけ。** 確かめられないものを青にしない。
- **赤は、食い違いを見つけた時だけ。** 怪しい「気がする」だけでは赤にしない（それは黄）。
- **文章のうまさを見ない。** 攻撃する側がいくらでも直せるものに頼らない。
- **決定的に。** 同じ入力には同じ答え。乱数・時刻・通信・AI を使わない。
- **リンク先へアクセスしない。** 文字列だけで判定する。
- **誤った赤の害も数える。** 赤が出すぎると、利用者は赤を無視するようになります。本物の連絡でよく見る書き方で赤にならないか、必ず見本で確かめます。

### 手順

1. **実際にありそうな文面で、困っていることを書く。** Issue に「この文面が、今はこの色になる。本当はこうあるべき」と書きます。実在の人の名前・電話番号・住所は入れず、攻撃側の住所には `example`（`evil.example` など、例のために取っておかれた住所）を使います。
2. **SPEC.md を先に直す。** 規則の正は SPEC.md です。新しい理由のコードは表に足します。
3. **Python（`python/kango/__init__.py`）を直す。**
4. **Swift（`swift/Sources/Kango/Judge.swift`）を同じように直す。** 正規表現は、Python と同じ文字列にします。文言も同じにします。
5. **両方のテストに、同じ見本を足す。** 「こうなるべき」見本と、「こうならないべき」見本（本物の連絡が誤って黄・赤にならないこと）の両方を入れます。
6. **できないことが変わったら、README の「できないこと」と [守れる範囲](threat-model.md) を直す。** 表は勘合を動かした答えをそのまま書きます（テストが確かめます）。
7. **CI（data・python・swift）がすべて緑になってから** Pull Request を出します。

### 版の上げ方

答えが変わる変更は、版（`python/pyproject.toml` の `version` と、README の `pip` の行）を上げます。リリースを作ると、`release-check` が外の開発者と同じやり方（URL から入れる）で動くかを確かめます。リリースの説明には、どんな文面の色が変わるのかを書いてください。
